# Agent 长程任务的可控性与状态管理

## 1. Agent 运行过程中的暂停/终止机制

Agent 的暂停与终止是一个**分层**的问题，需要从两个层面分别实现。

### 1.1 Agent 框架（Harness）层面的控制点

这是上层逻辑的“软中断”，依赖于在代码的关键路径上设置检查点。

- **实现原理**：在**调用 LLM 之前**和**执行工具之前**，检查一个全局的中断标志（Interrupt Flag）。
- **决策逻辑**：
    - **用户发出新指令**：放弃当前任务上下文，用新输入重置对话并重新开始。
    - **用户要求终止**：直接退出循环，不再进行后续的 LLM 调用和工具执行。
- **特点**：这是 Agent 框架自身的流程控制，与底层模型无关。

### 1.2 模型推理引擎层面的终止

这是底层计算的“硬中断”，用于释放 GPU 等计算资源。

- **澄清误区**：**无法**在神经网络层与层之间“插桩”来精确暂停和恢复推理。保存每一层的激活值在工程上不可行。
- **真实实现**：基于 **请求级中断（Request Abortion）**。推理引擎（如 vLLM）会在**当前计算步骤（Step）完成后**检查中断信号，从而停止为该请求分配后续计算。
- **两个阶段的可中断性**：
    - **Prefill 阶段**：通过 **分块预填充（Chunked Prefill）** 技术，将长 Prompt 切分为多个计算块。每个块完成后都是可中断点，无需等待整个 Prefill 完成。
    - **自回归（Decode）阶段**：在生成**每一个 Token 后**检查中断信号，决定是否继续生成下一个 Token。
- **本质**：所有模型的终止逻辑在核心上是一致的（中断 HTTP 流/请求），但具体实现（如是否返回部分生成内容）因平台而异。

## 2. Kimi K3（AgentENV）的快照机制解析

K3 的“快照”能力常被误解。它并非保存 Agent 的业务状态，而是针对**执行环境（沙箱）** 的系统级快照。

### 2.1 快照保存的是什么？

- **沙箱的“物理现场”**：基于轻量级虚拟机（Firecracker）的完整状态。
    - **文件系统**：所有文件、目录、已安装的软件和依赖。
    - **内存状态**：沙箱内进程在快照时刻的内存数据。
    - **增量存储**：只记录自上次快照以来被修改的部分（内存页和文件），效率很高（<100ms）。

### 2.2 快照不保存什么？

- **Agent 的业务逻辑状态（Harness 状态）**：例如任务进度（已执行到第几步）、中间产物（已生成的摘要、分析结果）、多轮对话历史等。
- **原因**：这些数据存在于 Agent 框架的内存或外部数据库（如 Redis）中，与沙箱（那台“临时电脑”）是完全独立的进程和存储空间。快照无法“理解”或“接管”业务逻辑。

### 2.3 快照能力的适用场景

- **最适合**：对**“一次性、确定性、环境依赖型”**的子任务进行快照。例如：已完成环境配置（Python + 依赖库）的沙箱、已加载大型数据集的沙箱。可通过分叉（Fork）并行执行不同脚本，省去重复初始化环境的时间。
- **不适合**：保存 Agent 自身的任务进度或决策路径。

## 3. 长程 Agent 任务的状态管理策略

对于需要长时间运行的 Agent，必须将“业务状态”和“环境状态”分开管理。

### 3.1 业务状态管理（Agent 框架负责）

- **内容**：任务进度、已调用的工具列表、中间计算结果、对话上下文、用户偏好等。
- **存储方案**：使用外部持久化存储，如**数据库（PostgreSQL）** 或**缓存（Redis）**。
- **恢复逻辑**：任务中断后，Agent 框架从数据库读取业务进度，从而“接续”之前的思路。

### 3.2 环境状态管理（沙箱负责）

- **内容**：执行代码所需的操作系统、依赖库、临时文件、内存中的进程等。
- **管理工具**：AgentENV 或类似沙箱平台。
- **恢复逻辑**：从快照快速恢复整个执行环境，省去重新安装依赖和准备数据的时间。

### 3.3 协同工作流

1.  **Agent 框架** 维护业务状态（例如：任务已执行到第 5 步，中间文件在 `/workspace/data.csv`）。
2.  当 Agent 决定执行某个代码块时，调用 **AgentENV API**。
3.  AgentENV 从快照恢复沙箱环境。
4.  环境恢复后，Agent 框架将业务状态（如步骤 5 的指令）注入沙箱，继续执行。
5.  执行结果通过 API 返回给 Agent 框架。

## 4. K3 沙箱（AgentENV）与腾讯云 Agent Runtime 对比

两者在“暂停/恢复”思路上相似，但在实现和计费模式上有显著区别。

| 特性 | Kimi K3 (AgentENV) | 腾讯云 Agent Runtime |
| :--- | :--- | :--- |
| **核心机制** | 基于 Firecracker 微虚拟机的沙箱，支持环境**暂停/恢复**、快照和分叉。 | 基于**存算分离**架构的沙箱执行层，支持按需创建和**暂停/恢复**。 |
| **计费模式** | 按 **Token 使用量**计费，而非按沙箱运行时长。 | 明确采用**暂停状态不计费**，按任务实际执行时间（秒级）付费。 |
| **计费粒度** | 按业务消耗（Token）计费 | 按资源占用时间计费 |
| **开源与否** | **完全开源（MIT 协议）**，可自行部署。 | 腾讯云托管服务，非开源。 |

## 5. 补充关键知识点

- **K3 沙箱并非必须搭配 K3 模型**：AgentENV 是一个独立平台，可以搭配任何 LLM 使用。
- **集成方式**：你的 Agent 框架和 AgentENV 沙箱在 K8s 中**无需合并**，通过 **HTTP API** 通信即可。快照的恢复对通信接口是透明的，不影响数据传递。
- **计费误解澄清**：K3 的“暂停”节省的是**计算资源费**（如 CPU/内存），但**模型 API 调用费**（按 Token 计费）依然产生。腾讯云 Agent Runtime 的“暂停”则直接不计算资源占用时长。
