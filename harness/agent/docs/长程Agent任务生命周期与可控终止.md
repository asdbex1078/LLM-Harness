# 长程 Agent 任务生命周期与可控终止

## 1. 为什么需要单独设计终止机制

长程任务通常同时包含三类工作：模型推理、工具执行和外部副作用。用户点击“停止”时，系统需要回答三个不同的问题：

1. 是否还允许 Agent 继续做下一步决策？
2. 当前正在执行的模型请求或工具能否被取消？
3. 已经发出的外部操作如何确认结果、重试或补偿？

因此，“终止任务”不是设置一个布尔变量，而是一个带持久化状态、取消协议和收尾流程的生命周期管理问题。

## 2. 任务状态模型

建议把任务状态持久化，而不是只保存在 Worker 内存中：

```text
CREATED -> RUNNING -> SUCCEEDED
                   -> FAILED
                   -> TIMED_OUT
                   -> CANCELLING -> CANCELLED
                   -> PAUSING -> PAUSED -> RESUMING -> RUNNING
```

状态转换必须由服务端原子更新，并记录 `version` 或等价的乐观锁字段。这样可以避免“取消请求”和“任务完成回写”同时到达时互相覆盖。

每个任务至少保存：

- `task_id`、`status`、`version`
- 当前阶段和下一步动作
- 已完成的工具调用及其结果引用
- 仍在执行的请求 ID
- 取消原因、操作者和时间
- 最近一次心跳和最后更新时间

## 3. 取消语义

### 3.1 用户主动取消

服务端先将任务从 `RUNNING` 原子更新为 `CANCELLING`，再向 Worker 发送取消信号。Worker 收到信号后：

1. 不再发起新的 LLM 请求；
2. 不再启动新的工具调用；
3. 尝试取消当前可取消的请求；
4. 等待已发出的外部操作进入可确认状态；
5. 写入最终结果并转为 `CANCELLED`。

如果当前操作不可取消，不能伪造“已取消”。应记录 `CANCELLING`，直到收到明确结果、超时或进入人工处理队列。

### 3.2 新指令抢占

新指令不等于取消旧任务。系统应先判断新指令是否：

- 继续当前任务；
- 修改当前任务；
- 取消当前任务并创建新任务；
- 与当前任务无关。

只有明确产生抢占关系时，才取消旧任务。新任务应携带 `parent_task_id` 或 `supersedes_task_id`，保证审计链完整。

### 3.3 超时终止

超时至少分为三种：

- 单次 LLM 请求超时；
- 单次工具调用超时；
- 整个任务超过截止时间。

局部超时可以重试或跳过；任务级超时则进入 `CANCELLING`，执行与用户取消相同的收尾流程。重试必须使用幂等键，避免超时后重复产生外部副作用。

## 4. 取消检查点与请求取消

Harness 层应在以下位置检查取消状态：

```text
读取任务状态
  -> 调用 LLM 前
  -> 选择工具前
  -> 工具调用前
  -> 工具返回后
  -> 写入阶段结果前
  -> 进入下一轮前
```

检查点只能阻止“下一步动作”。已经交给底层服务的请求，需要使用该服务提供的取消接口、连接关闭机制或取消 token。两者不能混为一谈。

对于流式 LLM 请求，客户端断开连接通常只能表达“不再接收结果”；服务端是否立即停止推理，取决于推理服务的实现，必须以该服务的官方文档和实测结果为准。

## 5. 工具调用与外部副作用

工具调用应分为两类：

### 可安全取消的操作

例如本地计算、只读查询、可中止的网络请求。取消后可以直接结束，但仍需记录请求是否已经发出。

### 不可回滚或需要补偿的操作

例如发送消息、创建订单、修改数据、触发部署。此类操作必须：

- 在请求中携带幂等键；
- 记录 `intent_created`、`request_sent`、`result_received` 等事件；
- 超时后先查询结果，再决定是否重试；
- 必要时进入补偿或人工确认状态。

“Worker 进程结束”不代表外部操作没有发生。

## 6. 暂停、恢复与终止的区别

暂停表示任务仍然有效，只是暂时不继续执行；终止表示任务不再继续推进。暂停恢复至少需要保存：

- 当前任务状态和版本；
- 已完成步骤及产物引用；
- 下一步动作及其前置条件；
- 未完成请求和外部操作状态。

沙箱快照只能解决执行环境恢复问题，例如文件系统、进程和依赖是否保留。它不能自动替代 Agent 业务状态、任务数据库、对话历史或外部系统状态。恢复长程任务时，必须同时恢复业务状态，并重新确认未完成的外部操作。

## 7. 崩溃恢复与重复执行

Worker 可能在工具请求发出后、结果写回前崩溃。恢复流程不能简单地从“最后一个成功步骤”继续，而应先扫描未决操作：

```text
读取任务状态
  -> 查找未完成的工具调用
  -> 使用幂等键查询外部结果
  -> 已成功：补写结果
  -> 未执行：安全重试
  -> 状态未知：保持待确认，不自动重复副作用
```

任务状态、事件日志和工具结果应具备可追溯关联，至少能通过 `task_id` 和 `tool_call_id` 还原完整过程。

## 8. 推荐的事件记录

事件日志建议采用追加写入：

| 事件 | 含义 |
|---|---|
| `task_started` | 任务开始运行 |
| `cancel_requested` | 收到取消请求 |
| `llm_request_started` | 发起模型请求 |
| `tool_request_started` | 开始工具调用 |
| `external_request_sent` | 外部请求已写出 |
| `tool_result_received` | 收到工具结果 |
| `cancel_observed` | Worker 在检查点观察到取消 |
| `task_cancelled` | 任务完成取消收尾 |
| `task_recovered` | 任务从持久化状态恢复 |

事件时间应由服务端统一生成，并保留请求 ID、幂等键和状态版本。这样才能区分“准备发送”和“请求已真正发出”。

## 9. 最小实现方案

一个可落地的最小架构包括：

1. **Task Store**：保存任务状态、版本、阶段和截止时间；
2. **Worker**：执行 LLM 与工具循环，在检查点读取取消状态；
3. **Cancellation Channel**：通过数据库轮询、消息队列或进程内信号传递取消请求；
4. **Operation Log**：记录工具调用和外部请求生命周期；
5. **Recovery Worker**：处理超时、崩溃和状态未知的操作；
6. **Idempotency Layer**：防止重试造成重复副作用。

## 10. 官方资料与适用边界

以下资料支持本文的基础判断：

- [Kubernetes Jobs：终止 Job](https://kubernetes.io/docs/concepts/workloads/controllers/job/#terminating-a-job)：删除或终止工作负载不等同于业务副作用回滚。
- [Firecracker：Snapshots](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)：快照描述的是微型虚拟机运行环境的保存与恢复能力。
- [vLLM：Stopping generation](https://docs.vllm.ai/en/latest/serving/openai_compatible_server.html)：请求停止行为属于推理服务接口能力，不能从 Harness 层统一推断。
- [PostgreSQL：事务隔离与并发控制](https://www.postgresql.org/docs/current/mvcc.html)：持久化状态更新需要处理并发读写和一致性。

本文没有据此推断某个具体厂商 Agent Runtime 的计费、快照耗时、内部调度实现或模型推理中断粒度。此类结论必须引用对应产品的当前官方文档或实测记录。

## 11. 验收清单

- 取消后不会再发起新的 LLM 或工具请求；
- 正在执行的请求有明确的取消结果或待确认状态；
- 外部副作用具备幂等键和结果查询路径；
- Worker 崩溃后不会盲目重复执行；
- 暂停恢复后任务能从明确的下一步继续；
- 所有关键时间点和状态转换可通过事件日志还原；
- 厂商特性与通用机制分开，并有官方资料或实测证据支持。
