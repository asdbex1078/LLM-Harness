# Knowrary 开发实施计划

> 目标：逐步交付“Markdown 知识文件 → 图谱结构视图 → Inbox → 手工布局持久化 → 历史视图 → Agent 辅助”的本地系统。
> 原则：先打通可验证闭环，再增加自动化；每个阶段都有独立产物和验收标准。

## 1. 总体架构与职责

```text
Markdown vault → 本地服务（解析、索引、布局、写回、监听） → Vue 3 + X6 前端
```

Markdown 负责知识内容和关系；`.knowrary/layout.json` 负责结构视图；`.knowrary/review-log.json` 负责复习记录；`.knowrary/index.json` 是可重建缓存；ChangeSet 是所有 Markdown 写回的唯一入口。

本地服务用 **Python 3.11+ / FastAPI**，与 `tools/knowrary/knowrary.py` 同栈；前端 Vue 3 + X6 的构建产物提交入库，运行期不需要 Node。LLM 由 `.knowrary/llm.local.json` 配置（多 provider，learn / review 双角色），详见设计文档 3.11。

## 3. 阶段 0：规范和样例数据

### 工作项

1. 创建 `vault/`、`nodes/`、`fields/`、`assets/` 和 `.knowrary/`。
2. 手动编写 10～30 个节点，覆盖结构、依赖、演化、对照和 stub。
3. 创建 `relation-types.json`，登记关系族、正向类型、互逆和对称类型。
4. 准备无 `year` 的结构节点、有 `year` 的历史节点和有效期节点。
5. 在 git 中提交初始 vault。
6. ✅ LLM 配置文件 `.knowrary/llm.local.json`（模板 `llm.example.json`）与 learn / review 双角色，`knowrary article` 走配置，`knowrary llm list / test` 可查（2026-09-10 完成）。

### 验收

每个节点能被 Obsidian 打开，引用使用稳定 id，样例覆盖未知目标、重复关系和缺失年份。

## 4. 阶段 1：解析器与索引（2026-09-10 完成）

### 工作项

1. ✅ 解析并校验 frontmatter（必填字段、id 合法性、status 枚举、year / 区间、布局字段混入）。
2. ✅ 扫描约定目录（`nodes/`、`fields/`），忽略 `.knowrary/backup`、隐藏目录、README 和临时文件。
3. ✅ 解析 `::` 关系语法，兼容旧箭头语法。
4. ✅ 关系归族、互逆归一（canonical 翻转）、对称边按 id 定向、两侧重复维护合并为一条边、反链用节点 in / out 邻接表表达、stub 识别（`status: stub` 与未创建目标的虚拟占位）。
5. ✅ 输出 `schema_version` / `revision` / `generated_at` / `content_hash` / `nodes` / `edges` / `families` / `stubs` / `stats` / `errors` / `warnings`；原子写入。
6. ✅ 命令 `python3 tools/knowrary/knowrary.py index --vault <path>`（`--stdout` / `--force` / `--strict` / `--out` / `--max-warn`）。计划里原写作 `kg-graph index`，实际统一到既有的 `knowrary` CLI。

### 产物

- `tools/knowrary/core/`：`mdio` / `relations` / `parser` / `index` / `schema` / `diagnostics`，CLI 与阶段 2 的 FastAPI 服务共用同一套解析，`knowrary.py` 变成薄壳，`check` 复用 index 的诊断。
- `tools/knowrary/tests/run.py`：零依赖自测 24 个用例。

### 验收

- ✅ 索引可重建且结果一致：内容哈希相同时 revision 与 generated_at 都不变、不落盘，重复生成逐字节一致。
- ✅ 非法 YAML（`bad_yaml`）、未知目标（`unknown_target`，同时生成虚拟 stub 不丢边）、非法年份（`bad_year` / `year_range_inverted`）都有诊断，另有重复 id、非法关系行、布局字段混入、未登记类型、重复维护、演化缺年份、正文死链等。
- ✅ 修改 / 新增 / 删除 md 后节点和边正确更新，revision +1。
- ✅ 真实 vault（72 节点 / 214 边）0 错误 9 警告，索引契约校验通过。

## 5. 阶段 2：结构视图与布局持久化（2026-09-10 完成）

### 工作项

1. ✅ FastAPI + uvicorn 服务（`server/`，依赖装在项目内 `.venv`）与 Vue 3 + Vite 前端（`web/`，构建产物 `web/dist` 入库、运行期零 Node）；pydantic v2 定义三份契约（index 只读 / layout + LayoutPatch / ChangeSet 留给阶段 3）。
2. ✅ `GET /api/index`（按 md 文件指纹缓存，变化即重建并落盘）、`GET /api/layout`（附 orphans 与 index_revision）、`GET /api/health`。
3. ✅ layout 契约：`schema_version` / `revision` / `updated_at` / `viewport` / `groups` / `nodes` / `refs` / `notes` / `images` / `edges`；首次打开按 `field` 建顶层分组、按 `nodes/` 子目录建二级分组、组内网格排列（生成逻辑在零依赖的 `core/layout.py`，CLI `knowrary layout init` 共用）。
4. ✅ X6 注册纯 SVG 的 `kg-node`（rect + 2 个 text）与 `kg-group`，五个关系族各一种线型；draft 虚线浅填充、stub 灰虚线、孤立记录红色虚线；边标签只在 zoom > 0.8 渲染。
5. ✅ 分组嵌套（parent/children + embedding，拖节点进框即改归属）、节点拖拽、拖空白平移、滚轮缩放、shift 框选、选中后右侧面板显示索引元数据与出入边。
6. ✅ `PATCH /api/layout`：JSON Merge Patch 语义（条目级合并、null 删除、列表整体替换），前端 300ms 节流合并、视口 1s 节流，服务端临时文件 + rename 原子写入。
7. ✅ 启动与每次读取都校验 layout 引用，缺失的节点 / 引用卡 / 边 / 图片 / 分组进 `orphans` 并在画布上以红色虚线显示，不自动删除。

### 产物

- `server/`：`paths` / `contracts` / `index_service` / `layout_store` / `app` + `dev.sh` + `requirements*.txt` + `tests/run.py`（16 个用例）。
- `web/`：`src/api.js`、`src/canvas/{shapes,render,patcher}.js`、`src/App.vue`、`vite.config.js`，构建产物 `web/dist/`；`web/tests/e2e_canvas.py` 用真无头 Chrome 派发真实鼠标事件跑 6 个端到端用例（临时 vault + 独立端口，不动仓库布局）。
- CLI 新增 `knowrary layout init/check`；`core/layout.py` 承载初始布局生成与孤立引用判定。

### 边的可读性（阶段 5 的两项提前做）

72 节点 193 边全画出来是一团麻：结构族 86 条里有 74 条两端同框（嵌套已表达）、26 组平行边完全重叠、全图默认 `router: 'orth'` 绕成迷宫。处理为：

1. 结构族默认不画线（设计文档 3.6），工具条可勾开；
2. 全图默认直线路由，`orth` 只留给阶段 3 的交互式连线；手工调过拐点的边仍按 layout 存的 router 渲染；
3. 同一对节点的多条边按法向错开成分离的弧线；
4. **跨分组边聚合**成「分组 A → 分组 B (n)」一束（粗细随条数），点它展开这对分组之间的明细、再点收起；
5. **悬停 / 选中高亮**：相关边加粗置顶，其余边淡到 0.07。

效果：一屏从 193 条散线降到 60 条组内边 + 16 束跨组边。

### 过程中修掉的三个真 bug（只有真交互才暴露）

1. X6 `embedding.frontOnly` 默认为 true：落点上盖着别的节点时，被拖的节点只解除了旧分组、认不到新分组，归属变成 null。改为 `frontOnly: false` + 自定义 `findParent`（按面积排序命中最内层分组）。
2. 用 `requestAnimationFrame` 放开"初始渲染不写盘"的守卫：后台标签页与无头浏览器里 rAF 不触发，守卫永不放开，用户的拖动被静默丢弃。改为首次真实交互（mousedown / wheel / 点适应窗口）放开，并在入队前与本地镜像比对跳过空写。
3. 程序化重渲染（切关系族、展开聚合束）会重新 `zoomTo` / `translate`，触发视口保存，每次切换都白涨一个 revision。加 `applyingViewport` 标志隔离。

### 验收

- ✅ 打开 <http://127.0.0.1:8765/> 就能看到样例图：2 个顶层分组、8 个二级分组、72 节点、193 边（无头 Chrome 截图核对过族色线型、stub 虚线、工具条统计）。
- ✅ 真实拖拽链路（无头 Chrome 派发真鼠标事件）：拖节点跨分组改归属、拖分组带着子节点一次性落盘、无位移不产生空写、刷新后位置与归属保持且刷新本身不写盘。
- ✅ 拖动后刷新与重启服务位置保持：PATCH → revision +1 → 重启进程再读盘位置不变。
- ✅ layout 修改不改变 Markdown：对全 vault 的 md 做哈希，PATCH 前后一致。
- ✅ 旧 revision 提交被拒绝：返回 409 + `current_revision`，且不写盘；前端自动重新拉取后重放本地改动。
- ✅ 非法补丁（新增条目缺字段、未知字段、引用不存在的分组、自己当父分组、缺 base_revision）一律 422 且不写盘。
- ✅ layout.json 损坏时返回 500 并保留原文件，不覆盖用户数据。

## 6. 阶段 3：节点详情与 Markdown 写回

### 工作项

1. 实现 `GET /api/node/:id`，返回原文、元数据和渲染内容。
2. 增加右侧详情面板和 Obsidian 打开按钮。
3. 定义新增、修改、删除边及修改 frontmatter 的 ChangeSet。
4. 展示变更预览，包含目标文件和内容片段。
5. 复用 `knowrary.py` 的区块解析，只改 `## 关系` 区块和允许修改的 frontmatter 字段，其余原文逐字保留。
6. 写回前生成 `.knowrary/backup/<timestamp>/` 快照。
7. 写回后重新解析、更新 revision 并通过 WebSocket 刷新。
8. 对单文件加写锁并检查 hash，外部修改后拒绝覆盖。

### 验收

未确认的 ChangeSet 不改文件；确认后 Obsidian 可正常打开；正文、代码块、列表保持原格式；外部修改不会被覆盖。

## 7. 阶段 4：Inbox 与 Digest

### 工作项

1. 实现 `GET /api/inbox`，列出不在 layout 中的节点。
2. Inbox 托盘拖入画布后创建 `draft` 或 `final` 条目。
3. 实现 `GET /api/digest`，展示草稿、跨分组桥、重复候选和 stub。
4. 草稿只在已有分组框内找空位，不移动 final、不扩大分组。
5. 增加定稿操作和草稿超期提示。
6. 复习提醒：`.knowrary/review-log.json`，固定间隔 1/2/4/7/15/30 天算 `next_due`；`GET /api/review/due`、`POST /api/review/:id`；Digest 增加"待复习"栏，结构视图到期节点角标；命令行 `knowrary review-due`。

### 验收

新建 Markdown 能进入 Inbox；拖入并刷新后位置和状态不变；分组无空位时留在 Inbox；Digest 能列出跨分组关系和 stub；只有 `learned` 没有复习记录的节点按 learned+1 天到期；点"已复习"后 next_due 按间隔表推进且不改 md。

## 8. 阶段 5：LOD 与结构视图完善

### 工作项

1. 分离完整图数据和 X6 可见投影。
2. 按缩放级别折叠分组，显示簇摘要。
3. 设常规可见元素目标 300～600，1500 为降级上限。
4. 支持钉住展开/折叠、跨分组边聚合和恢复。（聚合与展开/收起已在阶段 2 提前完成，此处只剩折叠钉住）
5. 增加关系族过滤、搜索居中、悬停高亮。（关系族过滤、悬停高亮、跨分组边聚合已在阶段 2 提前完成，此处只剩搜索居中）
6. 增加引用卡、便签、图片和手工边拐点。
7. 用 X6 History 管理布局操作；Markdown 写回仍走确认流程。

### 验收

超出预算时自动折叠；折叠展开不丢数据；搜索可定位 Inbox、画布和 stub；500～1000 节点下仍可完成基本操作。

## 9. 阶段 6：历史视图

1. 过滤有 `year` 的节点和符合规则的边。
2. X 轴按年份；顶部时间线选择器可选 layout 分组任意层级，Y 轴按所选分组的直接子分组分泳道（选"全部"时按 field）。
3. 增加紧凑模式、时间滑块和渐显动画。
4. `被激活` 关系使用金色虚线和动画。
5. 多选叠加多条时间线；有效期过滤。

验收：无 `year` 的节点不进入历史图；缺年份的演化边显示诊断；选中 JVM 分组只看到 JVM 节点且泳道为其子分组；滑块按年份显示节点和边；历史视图不修改结构布局。

## 10. 阶段 7：Agent 能力

1. learn 复用 `knowrary article` 的提示词与 apply 流程，review 重建；两者分别走 learn / review 角色，统一输出 ChangeSet。
2. 增加关系校验，返回结论、置信度、依据和待确认项。
3. 增加 Curator，为 Inbox 节点推荐分组并说明理由。
4. 增加重复检测和合并预览，展示受影响引用。
5. 增加跨分组桥、孤岛、stub 和长期 draft 推荐。
6. 未登记关系只能进入 `proposed_types`，不能直接改类型表。

验收：Agent 建议可转成 ChangeSet；未确认不修改 Markdown；每条建议有证据或理由；批量建议可逐条接受、拒绝和撤销。

## 11. 阶段 8：性能、恢复与发布

1. 生成 1000、3000、6000、10000 节点测试数据。
2. 测量索引生成、首屏、拖动、缩放、折叠和内存。
3. 使用真实节点、分组、便签、图片和边样式重复压测。
4. 验证服务重启、索引重建、layout 损坏恢复和备份恢复。
5. 验证 Obsidian 外部编辑、多标签和写锁冲突。
6. 增加日志、错误页、诊断导出和最小使用说明。
7. 将 schema 版本、迁移策略和兼容性写入发布文档。

发布标准：任何写回失败都不丢原文件；6000 节点以内通过 LOD 保持可操作；超规模时明确降级；首版不承诺外部图稿迁移和多人协作。

## 12. 推荐开发顺序

```text
规范与样例 → 解析器与 index → layout 读写 → X6 结构视图
→ ChangeSet 安全写回 → Inbox / Digest → LOD 与搜索
→ 历史视图 → Agent → 性能与发布
```

每完成一个阶段都保留可运行版本，用真实 vault 做一次端到端验证。后续阶段只能依赖稳定的数据契约，不直接读取前端内部状态。
