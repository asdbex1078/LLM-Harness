# 个人认知图谱系统（Personal Knowledge Graph System）
## 需求文档 & 技术架构文档

---

## 第一部分：项目概述

### 1.1 项目愿景

构建一个**可编辑、可回放历史、可全局预览、可渐进下钻**的个人认知图谱系统。它不只是一个笔记工具，也不是一个静态思维导图，而是一个**动态的知识演化沙盘**——能把一个人的整个知识体系（技术史、法律、医学、个人学习路径等）呈现为一张可交互、可编辑的图网络，并支持 AI Agent 参与知识的抽取、校验与推荐。

### 1.2 核心命题

| 传统工具 | 问题 | 本系统的回答 |
| --- | --- | --- |
| ProcessOn / 思维导图 | 只能树状，无法表达多源交汇、跨代激活 | 有向无环图，多类型边 |
| Obsidian 图谱 | 边无类型、无时间、无方向语义 | 边有 relation、year、方向 |
| Neo4j + Browser | 面向查询，不适合阅读与编辑 | 自研前端渲染，面向认知 |
| X6 单画布 | 节点一多就卡 | WebGL 全局图 + X6 局部编辑双层架构 |

### 1.3 一句话总结

**全局用 WebGL 看认知体系（万人级节点），局部用 X6 做精细编辑（百人级节点），底层用 Markdown 存内容和关系，Agent 负责扩展和校验。**

## 第二部分：需求文档

### 2.1 用户画像

- **核心用户**：学生、学习党、研究者、知识工作者
- **典型场景**：
    - 梳理一门学科的发展史（如 NLP、计算机体系）
    - 构建法律知识网络（法条、案例、学说、修订）
    - 记录个人学习路径，看见自己的认知边界
    - 跨领域知识交汇的探索（AI + 法律、医学 + 统计）

### 2.2 功能性需求

#### F1. 节点与边的数据模型

**F1.1 节点（Node）**

每个节点对应一个 Markdown 文档，frontmatter 存元数据。

```yaml
---
id: transformer
name: Transformer
year: 2017
start_year: 2017
end_year: null            # 用于法律修订等时间敏感场景
field: NLP                # 领域，用于分层与着色
type: 模型架构             # 类型，用于节点形状/颜色
status: active            # active / deprecated / disputed
aliases: [自注意力模型]
tags: [深度学习, 序列建模]
desc: 基于自注意力机制的序列建模架构
---
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | 全局唯一，英文/拼音，用于图数据主键 |
| name | 是 | 显示名 |
| year | 是 | 关键时间，用于时间轴 |
| start_year / end_year | 否 | 法律、标准等有有效期的场景 |
| field | 是 | 领域，用于分层与颜色 |
| type | 是 | 节点类型（模型 / 法条 / 案例 / 人物 / 概念） |
| status | 否 | 状态，用于灰显或标记争议 |
| aliases | 否 | 别名，用于检索与合并 |
| tags | 否 | 自由标签 |
| desc | 是 | 一句话描述，用于全局图悬停 |

**F1.2 边（Edge）**

边不单独建文件，写在源节点 md 的正文“关联关系”区块里，用统一语法。

```markdown
## 关联关系
- 演进自:: [[attention-mechanism]] (2014) — 核心思想来源
- 借鉴:: [[cnn]] — 并行化思想
- 分支为:: [[bert]] (2018)
- 分支为:: [[gpt]] (2018)
- 被激活:: [[gpu]] (2017) — 训练依赖
- 影响:: [[loop-transformer]] (2024)
```

解析规则：`- <relation>:: [[<target_id>]] (<year>) — <note>`

**关系类型（初版，保持克制，不超过 8 种）**

| relation | 含义 | 视觉建议 |
| --- | --- | --- |
| 演进自 | 直接继承 / 改进 | 实线，粗 |
| 借鉴 | 思想来源，非直接继承 | 虚线 |
| 分支为 | 从当前节点分出 | 实线，带箭头 |
| 被激活 | 早期发明被后世重新使用 | 金色虚线（重点） |
| 修订 | 版本更替 | 实线，带时间标记 |
| 争议 | 存在对立观点 | 红色双向虚线 |
| 适用 | 案例适用于法条 | 细实线 |
| 影响 | 弱关联 | 浅色点线 |

> 关系类型要克制。一开始想出 20 种，真正有用的只有 5-6 种。类型太多图会变毛线球。

#### F2. 全局预览层（认知体系总览）

**F2.1 需求描述**

用户打开系统，第一眼看到的是**整个认知体系的全局图**，能一眼看出：

- 我有哪些领域（颜色分块）
- 时间跨度（X 轴）
- 哪些节点是核心枢纽（大小）
- 哪些是跨代激活（金色虚线）
- 哪些是孤岛（孤立节点，提示需要补充关联）

**F2.2 性能要求**

- 支持 10,000+ 节点、30,000+ 边
- 缩放、平移流畅（60fps）
- 首屏加载 < 3 秒（数据分片 + 渐进加载）

**F2.3 交互要求**

- **缩放分级（LOD）**：
    - 最远：只显示领域簇
    - 中距：显示大节点 + 名称
    - 近距：显示全部节点 + 边
- **时间轴滑块**：拖动到某年，只显示该年之前的节点，后面的逐渐“长出来”——实现**历史回放**
- **关系过滤**：勾选/取消某类 relation，图中对应边显隐
- **领域过滤**：只看某个 field
- **点击节点**：右侧弹出该节点的 md 内容
- **点击区域**：切换到 X6 编辑层

#### F3. 局部编辑层（X6）

**F3.1 需求描述**

从全局图点击某区域后，进入 X6 画布，只加载该区域内的节点（50-200 个），进行精修。

**F3.2 编辑能力**

- 拖拽节点改变位置（保存回 `x/y` 或布局参数）
- 拖拽锚点创建新边
- 右键边 → 修改 relation / note / year
- 双击节点 → 编辑文本（同步回 md）
- 从左侧 Stencil 拖入新节点
- 删除节点/边（二次确认）
- 撤销/重做（X6 内置 History 插件）

**F3.3 编辑后的同步**

编辑完成后，数据写回：

1. 前端 X6 → 生成 diff
2. 发送到本地服务（Node/Python）
3. 服务更新对应 md 文件
4. 服务重新生成 index.json
5. 全局图刷新

#### F4. 历史发展可视化

**F4.1 时间轴布局**

- X 轴 = year
- Y 轴 = field 分层（理论 / 体系 / 语言 / 算法 / 硬件）
- 力导向微调，避免重叠

**F4.2 跨代激活高亮**

GPU（1999）→ AI（2012）这类“迟到的重逢”，用金色虚线 + 动画流动效果，在全局图上极其显眼。

**F4.3 时间回放**

滑块拖动时，节点按 year 逐个浮现，边按 year 逐条生长。这是静态图永远做不到的。

#### F5. 底层文档系统

**F5.1 文档结构**

```
vault/
├── index.md                  # 总目录
├── fields/
│   ├── nlp.md                # 领域总览（中间节点）
│   ├── computer-history.md
│   └── law.md
├── nodes/
│   ├── transformer.md
│   ├── bert.md
│   ├── gpt.md
│   └── ...
└── assets/
```

**F5.2 中间节点 vs 底层节点**

- **中间节点**（如 `nlp.md`）：写领域概述，frontmatter 里用 `children: [...]` 列出子节点，充当目录。
- **底层节点**（如 `transformer.md`）：写完整内容，包括公式、代码、参考文献、技术实现细节。

**F5.3 内容承载**

每个底层节点的 md 可以承载：

- 技术实现文档（架构图、代码片段）
- 学习笔记
- 论文引用
- 个人思考
- 待办（"这里还没搞懂"）

X6 上只显示节点标题，双击打开完整 md。

#### F6. Agent 能力（后期）

**F6.1 关系抽取**

从 md 正文里用 LLM 抽取实体和关系，生成候选边，人工确认后入库。

**F6.2 关系校验**

"Transformer 真的借鉴了 CNN 吗？"——LLM 给出判断 + 依据，用户决定是否保留。

**F6.3 知识推荐**

"你写了 BERT，但还没写 RoBERTa、DeBERTa，建议补充。"

**F6.4 潜在方向生成**

在最新节点上，用虚线连出"潜在发展方向"的草稿，用户判断。

**F6.5 合并与去重**

识别 aliases 相同的节点，提示合并。

### 2.3 非功能性需求

| 维度 | 要求 |
| --- | --- |
| 性能 | 全局图 10k 节点 60fps；编辑层 200 节点无卡顿 |
| 数据量 | 单用户 10 万节点以内 |
| 离线 | 优先本地运行，数据不上云 |
| 可迁移 | md 文件是唯一真相源，随时可带走 |
| 可扩展 | 新增领域只需新增 md，不改代码 |
| 兼容 | 与 Obsidian vault 兼容，可直接读取 |

## 第三部分：技术架构文档

### 3.1 总体架构

```
┌─────────────────────────────────────────────────┐
│                  前端（Web）                      │
│  ┌──────────────────┐   ┌──────────────────┐    │
│  │  全局预览层        │   │  局部编辑层        │    │
│  │  Sigma.js/WebGL   │◄─►│  AntV X6          │    │
│  │  万级节点          │   │  百级节点          │    │
│  │  只读/缩放/筛选    │   │  拖拽/改边/加节点   │    │
│  └──────────────────┘   └──────────────────┘    │
│           ▲                      ▲               │
│           │     共享数据源        │               │
│           └──────────┬───────────┘               │
│                      │                           │
│              index.json (轻量索引)                │
└──────────────────────┼───────────────────────────┘
                       │ HTTP / WebSocket
┌──────────────────────┼───────────────────────────┐
│              本地服务（Node / Python）             │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐  │
│  │ md 解析器   │  │ 索引生成器  │  │ 写回器      │  │
│  └────────────┘  └────────────┘  └────────────┘  │
│  ┌────────────────────────────────────────────┐  │
│  │         Agent（LLM 调用层）                  │  │
│  │  抽取 / 校验 / 推荐 / 生成草稿                │  │
│  └────────────────────────────────────────────┘  │
└──────────────────────┼───────────────────────────┘
                       │
┌──────────────────────┼───────────────────────────┐
│              数据层（Markdown Vault）             │
│   *.md（frontmatter + 正文 + 关联关系）           │
│   可选：SQLite 缓存 / Neo4j（超大规模时）          │
└─────────────────────────────────────────────────┘
```

### 3.2 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 全局预览 | **Sigma.js**（WebGL） | 10 万节点级渲染，社区成熟 |
| 全局预览备选 | G6 WebGL 模式 / PixiJS | 若想统一 AntV 生态 |
| 局部编辑 | **AntV X6** | 图编辑器框架，拖拽/编辑/History 开箱即用 |
| 前端框架 | Vue 3 或 React | X6 对两者支持都好 |
| 布局算法 | ForceAtlas2（全局）、Dagre（局部） | 全局用 WebGL 力导向，局部用 DAG |
| 本地服务 | Node.js（Express/Fastify）或 Python（FastAPI） | 解析 md、生成索引、写回 |
| LLM | Claude / GPT / 本地模型 | Agent 能力 |
| 数据源 | Markdown + frontmatter | 人类可读、可迁移、兼容 Obsidian |
| 索引 | JSON（小规模）/ SQLite（大规模） | 轻量、快速 |
| 超大规模 | Neo4j（可选） | 需要 Cypher 查询时 |

### 3.3 数据流

**读路径（渲染）：**

```
md 文件
  → 解析器提取 frontmatter + 关联关系
  → 生成 nodes[] 和 edges[]
  → 输出 index.json
  → 全局层加载 index.json，WebGL 渲染
  → 点击区域 → 子集数据 → X6 渲染
```

**写路径（编辑）：**

```
X6 编辑操作
  → 生成 diff（新增/修改/删除）
  → POST 到本地服务
  → 服务更新对应 md
  → 重新生成 index.json
  → 全局层刷新
```

**Agent 路径：**

```
用户提问 / 定期触发
  → Agent 读 md 正文
  → LLM 抽取/校验/推荐
  → 生成候选变更
  → 用户确认
  → 写回 md
```

### 3.4 数据模型详解

**index.json 结构：**

```json
{
  "version": "1.0",
  "generated_at": "2026-09-10T10:00:00Z",
  "nodes": [
    {
      "id": "transformer",
      "name": "Transformer",
      "year": 2017,
      "field": "NLP",
      "type": "模型架构",
      "status": "active",
      "desc": "基于自注意力机制的序列建模架构",
      "x": null, "y": null
    }
  ],
  "edges": [
    {
      "id": "e_transformer_bert",
      "source": "transformer",
      "target": "bert",
      "relation": "分支为",
      "year": 2018,
      "note": ""
    }
  ],
  "fields": [
    { "id": "NLP", "name": "自然语言处理", "color": "#4A90D9" }
  ]
}
```

**md 解析规则：**

```python
# 伪代码
def parse_md(filepath):
    frontmatter, body = split_frontmatter(filepath)
    node = {
        "id": frontmatter["id"],
        "name": frontmatter["name"],
        "year": frontmatter.get("year"),
        "field": frontmatter["field"],
        "type": frontmatter["type"],
        "desc": frontmatter.get("desc", "")
    }
    edges = []
    for line in body:
        if match(r"- (\w+):: \[\[(\w+)\]\]"):
            relation, target = extract(line)
            edges.append({
                "source": node["id"],
                "target": target,
                "relation": relation,
                "year": extract_year(line)
            })
    return node, edges
```

### 3.5 全局预览层技术细节

**Sigma.js 配置要点：**

- **渲染器**：WebGL
- **节点渲染**：`drawCircle` 或自定义 `drawDisc`，按 field 着色，按度数决定半径
- **边渲染**：`drawLine`，按 relation 决定颜色/虚线；金色虚线用于"被激活"
- **标签**：仅在 zoom > 阈值时渲染，避免文字爆炸
- **LOD 策略**：
    - zoom < 0.3：只画领域簇（用社区检测算法预计算）
    - 0.3 < zoom < 1.0：画大节点 + 名称
    - zoom > 1.0：画全部节点 + 边标签

**布局：**

- 预计算：`ForceAtlas2` 离线跑一遍，把 x/y 存进 index.json
- 增量：新增节点时局部微调，不全量重算
- 时间轴模式：X 轴锁定为 year，Y 轴力导向

**性能优化：**

- 节点数 > 5000 时，启用四叉树空间索引
- 边用 WebGL 批量绘制，不用 SVG
- 懒加载：只渲染视口内的节点（视口裁剪）

### 3.6 局部编辑层技术细节

**X6 配置要点：**

- **画布**：`Graph` 实例，开启 `panning`、`mousewheel`、`connecting`
- **节点**：自定义 Vue/React 组件，显示标题 + 图标
- **边**：自定义 `Edge`，按 relation 渲染不同样式
- **插件**：
    - `History`：撤销/重做
    - `Stencil`：左侧拖拽面板
    - `Snapline`：对齐辅助线
    - `Selection`：框选
    - `Keyboard`：快捷键

**编辑与 md 同步：**

```javascript
// 监听编辑事件
graph.on('edge:change:target', ({ edge }) => {
  const data = edge.getData()
  pendingChanges.push({
    type: 'update_edge',
    source: data.source,
    target: edge.getTargetCellId(),
    relation: data.relation
  })
})

// 批量提交
async function commit() {
  await fetch('/api/apply-changes', {
    method: 'POST',
    body: JSON.stringify(pendingChanges)
  })
  refreshGlobalGraph()
}
```

### 3.7 本地服务技术细节

**职责：**

1. 扫描 vault 目录，解析所有 md
2. 生成 index.json
3. 接收前端编辑请求，写回 md
4. 提供 Agent API

**接口设计：**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/index | 返回 index.json |
| GET | /api/node/:id | 返回单个节点 md 内容 |
| POST | /api/apply-changes | 应用编辑 diff |
| POST | /api/agent/extract | 触发关系抽取 |
| POST | /api/agent/validate | 触发关系校验 |
| POST | /api/agent/suggest | 触发知识推荐 |

**写回 md 的注意事项：**

- 保留原有格式，只改动必要的部分
- 用 AST 解析（如 `remark`）而非正则，避免破坏
- 写回前备份，支持回滚
- 并发写加锁，避免冲突

### 3.8 Agent 层技术细节

**F6.1 关系抽取 Prompt 模板：**

```
你是一个知识图谱构建助手。以下是节点 "{name}" 的正文：

{body}

请从中抽取该节点与其他知识点的关系。输出 JSON 数组：
[
  { "relation": "演进自|借鉴|分支为|...", "target": "目标节点名", "year": 2017, "note": "简短说明" }
]

只输出 JSON，不要解释。
```

**F6.2 校验 Prompt：**

```
已知：{source} --{relation}--> {target}（{year}）
请判断这个关系是否成立，给出理由和置信度（0-1）。
输出 JSON：{ "valid": true, "confidence": 0.9, "reason": "..." }
```

**F6.3 推荐逻辑：**

- 找"度数低但领域重要的节点"（孤立节点）
- 找"同领域内被多次引用但未创建的节点"（红链）
- 用 LLM 生成"可能缺失的相关节点"列表

**Agent 的边界：**

- **只提议，不自动写入**。所有变更需用户确认。
- **LLM 有幻觉**，尤其历史年份和借鉴关系，必须人工校验。
- **批量操作要分批**，避免一次改太多无法审查。

## 第四部分：关键决策与注意点

### 4.1 核心决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 全局 vs 局部 | 双层渲染 | X6 扛不住大数据，WebGL 扛得住 |
| 数据源 | Markdown | 可迁移、可读、兼容 Obsidian |
| 边存储 | 写在节点 md 里 | 避免文件爆炸，符合人类直觉 |
| 关系类型 | 克制，≤8 种 | 太多会变毛线球 |
| 编辑同步 | 手动/批量提交 | 避免频繁写盘，便于审查 |
| Agent 权限 | 只提议 | 防幻觉污染知识库 |

### 4.2 常见坑与对策

| 坑 | 表现 | 对策 |
| --- | --- | --- |
| 图变毛线球 | 节点 > 200 后无法阅读 | 时间轴 + 领域过滤 + LOD |
| X6 卡顿 | 节点 > 500 掉帧 | 只加载局部子图 |
| md 解析破坏格式 | 写回后格式乱了 | 用 AST 解析，不用正则 |
| 关系类型爆炸 | 20 种关系，无法管理 | 强制收敛到 ≤8 种 |
| 时间字段混乱 | 有的写 year，有的写 date | 统一 schema，校验 |
| 循环依赖 | A 演进自 B，B 演进自 A | 建图时检测环，提示用户 |
| LLM 幻觉 | 编造年份和关系 | 人工确认 + 引用来源 |
| 数据丢失 | 编辑后 md 被覆盖 | 自动备份 + Git |

### 4.3 历史发展的特殊处理

- **时间轴是 X 轴**：全局图锁定 year 为横坐标，一眼看出先后
- **跨代激活用金色虚线**：GPU → AI 这种，必须视觉突出
- **时间回放**：滑块拖动，节点按 year 逐个浮现
- **分支用 Y 轴展开**：Transformer 之后，BERT 和 GPT 上下分叉
- **未来节点用灰色虚线**：Loop Transformer 之后的"潜在方向"，用虚线圈表示

### 4.4 法律场景的特殊处理

- **start_year / end_year**：法条有生效和废止时间
- **修订关系**：旧法 → 新法，用带时间标记的边
- **争议关系**：学说 A ↔ 学说 B，红色双向虚线
- **案例适用**：案例 → 法条，细实线
- **时间有效性过滤**：查 2020 年的法律状态，只显示当时有效的法条

### 4.5 性能优化的关键点

1. **索引与内容分离**：index.json 只存结构，不存正文
2. **预计算布局**：ForceAtlas2 离线跑，结果存盘
3. **视口裁剪**：只渲染可见区域
4. **边批量绘制**：WebGL 一次性画完，不用 SVG
5. **LOD**：远处不画文字，近处才画
6. **分片加载**：按 field 分片，按需加载

## 第七部分：边界与不适合的场景

### 不适合的场景

| 场景 | 为什么不适合 | 推荐工具 |

### 适合的场景特征

- 一个知识点同时属于多个维度
- 知识点之间有多种类型的关系
- 有跨时间的演化（版本更迭、新旧对比）
- 有跨领域的交汇
- 需要从不同角度切片查看
- 需要看"整个认知体系"
