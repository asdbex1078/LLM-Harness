# Knowrary（个人知识库 · 认知图谱系统）
## 第二版：需求文档 & 技术架构文档

> Knowrary = know + library。项目于 2026-09-10 由“个人认知图谱系统”更名，正文中“图谱”指其中的结构层。

> 修订日期：2026-09-10
> 本版聚焦一个可持续演进的本地 MVP：**手动创建 Markdown，系统负责解析、展示、保存布局，并通过 Inbox/Digest 管理增量知识。** ProcessOn 等外部图稿迁移暂不纳入范围。

---

## 第一部分：项目概述

### 1.1 项目愿景

构建一个**可手工布局、可全局纵览、可渐进下钻、可回放历史**的个人认知图谱系统。它的定位不是笔记工具（Obsidian 已经做得很好），也不是通用绘图工具（ProcessOn 已经做得很好），而是介于两者之间缺失的那一层：**一张由人决定结构、由程序负责生长的知识地图**。

数据层与 Agent 层沿用本仓库 vault 和 `tools/knowrary/knowrary.py`（解析、校验、导入、LLM 调用已就位；旧的 `kg.mjs` 与 knowage vault 已弃用），本项目新增的是**画面层**：一个读写 vault 的本地服务（Python），加一个基于 X6 的前端。

### 1.2 已尝试并否决的方案

| 方案 | 问题 | 结论 |
| --- | --- | --- |
| Obsidian Graph View | 力导向布局，边无类型无方向，层级、演化、串联全部丢失 | 只当调试用 |
| Obsidian Canvas | 连线只有一种贝塞尔曲线，分组只能是矩形，无折线，视觉粗糙 | 放弃 |
| 自动布局 HTML（kg render） | 分层、嵌套正确，但位置由算法决定，永远差一口气，约 70 分 | 降级为快速预览 |
| draw.io | 能力对齐 ProcessOn，但 SVG DOM 渲染大图卡顿，手感不如 ProcessOn | 放弃 |
| 外部图稿迁移 | 会引入格式映射、坐标和特殊图形兼容成本 | 暂不纳入首版，后续单独设计 |
| Sigma.js + X6 双引擎（第一版） | 两套样式、两套交互、两边同步；万级 60fps 是过度设计 | 收敛为 X6 单引擎 |

这些尝试共同指向一个结论：**好看的图之所以好看，是因为每个位置是人判断的。** 所以本系统的核心原则是：**结构由人定，机器只在人画好的框里面放东西。**

### 1.3 核心原则

1. **Markdown 是唯一真相源**：节点内容和关系全部在 `.md` 里，兼容 Obsidian，随时可带走。
2. **布局是数据，不是算法输出**：坐标、分组、折叠状态持久化在 `layout.json`，程序永远不移动用户定稿的节点。
3. **全局一张图**：不按领域拆成多张图，而是一个坐标空间加层级分组，缩小时折叠成簇，放大时展开细节。
4. **机器只做增量**：新节点最多放进它所属分组框内的空位，标为草稿；整体结构不碰。
5. **Agent 只提议不越权**：所有写入 md 的变更需用户确认。
6. **关系类型克制但可增长**：渲染只认 5 个"类型族"，具体类型可以自由增加，永不因为未知类型而丢边。

### 1.4 一句话总结

**一张 X6 全局图，缩小是簇、放大是细节，位置由人定稿、机器只放草稿，Markdown 存真相，有 year 的节点另开历史 tab。**

## 第二部分：需求文档

### 2.1 用户画像与使用习惯

- **核心用户**：学习面广的知识工作者（当前：计算机体系结构、C 语言、JVM、AI/LLM 并行学习）。
- **关键习惯**：**学一阵、攒一批、集中画图**。学习时不愿被"这个框放哪"打断；画图是单独找时间做的整理动作。
- **价值排序**：画面质量 > 自动关联与推荐 > 自动摆放。
- **规模预期**：当前 63 个节点，预期几年内几千个，需要为万级留余量。

这个习惯决定了工具形态：学习时只收集（Inbox），整理时一次处理一批（Digest），画面永远保持手工质量。

### 2.2 功能性需求

#### F1. 数据模型

**F1.1 节点（Node）**

一个节点对应一个 Markdown 文件，frontmatter 存元数据。

```yaml
---
id: transformer            # 全局唯一，缺省取文件名
name: Transformer
year: 2017                 # 可选。有 year 的节点进入历史视图
start_year: 2017           # 可选，法律/标准等有效期场景
end_year: null
field: NLP                 # 顶层领域，对应顶层分组
type: 模型架构              # 节点类型，影响图标/颜色
status: active             # active / deprecated / disputed / stub
aliases: [自注意力模型]
tags: [深度学习, 序列建模]
desc: 基于自注意力机制的序列建模架构
learned: 2026-08-14        # 导入时自动写入；复习记录不进 md，见 F8 与 .knowrary/review-log.json
---
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是（可省略，取文件名） | 图数据主键，写 `[[链接]]` 时使用 |
| name | 是 | 显示名 |
| field | 是 | 顶层领域，决定默认所属分组 |
| type | 否 | 节点类型 |
| **year** | **否** | 可选的历史事件元数据；有值时参与历史视图，没有时只参与结构视图 |
| start_year / end_year | 否 | 有效期场景 |
| status | 否 | `stub` 表示被引用但尚未写内容的空壳（红链） |
| aliases / tags | 否 | 检索与合并 |
| desc | 是 | 一句话，用于悬停和折叠卡片 |
| learned | 否 | 首次入库日期，程序维护；是遗忘曲线复习提醒（F8）的起点 |

> **year 的定位**：year 是节点的可选历史事件元数据，也是当前版本进入历史视图的开关。后续如需表达提出、发布、修订等多个时间点，可扩展为 `events: [{ year, type, note }]`，不破坏现有单值字段。

**F1.2 边（Edge）**

边写在源节点 md 正文的 `## 关系` 区块里，一行一条：

```markdown
## 关系
- 演化为:: [[bert]] (2018) — 双向编码分支
- 借鉴:: [[cnn]] — 并行化思想
- 部件:: [[multi-head-attention]]
- 类比:: [[高速缓存]] — 都是小而快的缓存挡在慢存储前面
```

解析规则：`- <类型>:: [[<目标 id>]] (<year>)? (— <note>)?`。`::` 是 Obsidian Dataview 的内联字段语法，Obsidian 内可直接查询。

现有 vault 使用的 `- 类型 → [[目标]]` 语法由解析器兼容读取，并提供 `kg migrate` 一次性转换为 `::` 语法。

**边的方向规则**：

- 每种类型有唯一的正向语义，边只写在源节点里，**反链由解析器推导**，不再双向回填（避免两处漂移）。
- 互逆类型成对声明（`属于` ⇄ `包含`），解析时归一为正向（统一存为 `包含`），用户在哪一侧写都可以。
- 边的 year 可选。默认不自动继承；只有在关系类型明确允许时才继承。演化类关系缺少有效年份时进入 review 警告，避免把推断时间伪装成事实。

**F1.3 关系类型族（Relation Family）**

渲染和分析只认族，不认具体类型。族固定 5 个，具体类型可增长。

| 族 | 含义 | 初始类型 | 结构 tab 渲染 | 历史 tab |
| --- | --- | --- | --- | --- |
| **结构** | 组成、归属、分类 | 包含、部件、属于、分类、实例 | **不画线，表现为嵌套**（可切换为画线） | 不画 |
| **依赖** | 下层支撑上层 | 依赖、基于、实现、前提、控制、编译目标 | 灰色细实线箭头 | 可选 |
| **演化** | 时间上的继承与替代 | 源自、演化为、扩展为、修订、被激活 | 橙色粗实线箭头 | **主线** |
| **对照** | 并列比较 | 对比、类比、争议 | 紫色虚线，无箭头 | 可选 |
| **弱关联** | 提及、参考 | 影响、相关、参考 | 浅色点线 | 不画 |

- 类型到族的映射存在 `tools/relation-types.json`，同时声明方向和互逆关系。
- LLM 产生未登记的类型时，**落到"弱关联"族并在 review 中提示归类**，不隐藏、不丢弃。这修复了第一轮实现中"新类型掉进未勾选的其他"导致边消失的问题。
- 类型族与 review（图分析推荐）的逻辑共用：前提缺失看依赖族，孤岛看全部，重复看结构族。

#### F2. 布局与视图数据

**F2.1 layout.json**

vault 根目录下 `.knowrary/layout.json`，只存视图信息，不存内容。核心约束：

- 坐标**不进 md frontmatter**。理由：坐标是视图不是内容；Obsidian 会把它显示出来；同一节点可能以引用卡形式出现在多处。
- 一个节点在 layout 中**只有一个本体位置**。
- 程序**永不修改** `state: final` 的条目的坐标。

**F2.2 节点三态**

| 状态 | 含义 | 渲染 | 谁能改坐标 |
| --- | --- | --- | --- |
| **inbox** | vault 有 md，layout 里没有条目 | 不在画布上，出现在 Inbox 托盘 | — |
| **draft** | 程序放的草稿位 | 虚线边框，浅色 | 程序可重放，用户可拖 |
| **final** | 用户拖过或点了"定稿" | 实线 | 只有用户 |

**F2.3 视图元素种类**

手绘图好看的要素必须有地方放：

| 元素 | 来源 | 说明 |
| --- | --- | --- |
| 知识节点 | md 文件 | 标题 + desc 摘要，双击打开 md |
| 分组框（Group） | layout | 可嵌套、可折叠、可命名、可着色。顶层分组默认对应 `field` |
| 引用卡（Ref） | layout | 指向另一处本体节点的虚线卡片，用于"JIT 同时属于编译原理和 JVM"，点击跳到本体 |
| 便签（Note） | layout | 自由文本，对应手绘图里的黄色便签 |
| 图片（Image） | layout + assets/ | 内存布局示意图、CISC 流程小图这类子图 |
| 连线拐点 | layout | 只有用户手动调过的边才记录 vertices，其余自动路由 |

**F2.4 分组层级**

三层：领域（field）→ 子领域 → 节点。分组与结构族边的关系：

- 结构族边（包含/部件）默认渲染为嵌套，即子节点画在父节点的分组框内。
- 分组框可以独立于结构族边存在（纯视觉分组），也可以由结构族边自动生成初始分组（仅用于草稿放置）。
- 用户拖节点进出分组框，**不改 md 里的关系**，只改 layout。是否同步成结构族边由用户在右键菜单里选择。

#### F3. 结构视图（主 tab）

**F3.1 一张全局图**

打开系统看到整张图，缩小时只见领域簇，放大时见节点与边。不按领域拆图。

**F3.2 LOD 折叠规则**

- 分组按缩放级别自动折叠/展开：`zoom < 0.35` 只展开顶层分组，`0.35 ~ 0.7` 展开到子领域，`> 0.7` 全部展开。阈值可配置。
- **可见元素预算**：目标是视口内 300～600 个 X6 元素；1500 个是允许的降级上限。超过上限时从最深层分组开始折叠。预算是性能保护阈值，不承诺在上限下始终达到 50fps。
- 用户可**钉住**某个分组保持展开或折叠，覆盖自动规则。
- 折叠后的分组渲染为一张卡片：分组名、节点数、3 到 5 个度数最高的节点名。
- 跨分组的边在折叠时**聚合为一条粗线并标数量**，展开后还原为原始边。

**F3.3 交互**

- 滚轮缩放、拖拽平移、框选、快捷键。
- 悬停节点：高亮它的所有边与邻居，其余变淡。
- 点击节点：右侧面板显示 md 渲染内容与全部关系。
- 双击节点：`obsidian://open?vault=knowage&file=...` 在 Obsidian 中打开。
- 右键节点：定稿 / 移到分组 / 创建引用卡 / 在 Obsidian 打开。
- 右键边：修改类型 / note / year（写回 md，需确认）。
- 关系族过滤：勾选/取消某个族，边显隐。
- 搜索：按 name / aliases / tags 定位并居中。

**F3.4 编辑**

- 拖拽节点、分组、便签、图片改位置 → 写 layout（状态变 final）。
- 拖拽锚点连线 → 生成候选边，选类型后写回 md。
- 从 Inbox 托盘拖入节点 → 写 layout。
- 删除节点：只从 layout 移除（回到 inbox）；删除 md 需在 Obsidian 里做。
- 撤销/重做：X6 History 插件，作用于 layout 层；md 写回不进 undo 栈，单独确认。

#### F4. 历史视图（第二个 tab）

**F4.1 参与规则**

- 只显示 frontmatter 有 `year` 的节点。
- 边：演化族默认显示；依赖族和对照族可选显示；边两端都有 year 才画。

**F4.2 布局**

- X 轴 = year，线性比例；提供"紧凑模式"把超过 20 年的空白段压缩。
- Y 轴 = 顶层领域泳道；泳道内按扫描线避让防重叠。
- 这是**浏览视图**，允许自动布局，因为 X 被时间锁死，不存在"位置由算法乱猜"的问题。历史视图的坐标不持久化。

**F4.3 时间回放**

- 时间滑块：拖到某年只显示该年之前的节点与边，向后拖时节点逐个浮现、边逐条生长。
- 跨代激活（`被激活` 类型，如 GPU 1999 → 深度学习 2012）用金色虚线加流动动画高亮。

**F4.4 时间线选择（历史分类）**

JVM 有 JVM 的历史，LLM 有 LLM 的历史，混在一张按顶层领域分泳道的图里看不清。因此：

- 历史 tab 顶部有"时间线"选择器，选项来自 layout 分组树的**任意层级**（JVM、LLM、GPU……），也可选顶层领域或"全部"。
- 选中一个分组：只显示该分组（含子分组）内有 `year` 的节点，泳道变为它的直接子分组。JVM 史、LLM 史各自成一条独立时间线。
- 可多选叠加：同时选 GPU 与 LLM 时两条线分泳道并排，跨线的 `被激活` 边照常画，用来看"一个领域的突破如何点燃另一个领域"。
- 不新增 frontmatter 字段：历史线跟着已经手工分好的分组走。将来若需要横跨多个分组的主题史（如"并行计算史"），再评估可选的 `timeline` 字段。
- **已否决：学习轨迹叠加**（以 `learned` 为第二条时间线）。我不需要看自己按什么顺序学，需要的是"什么该复习了"，见 F8。

**F4.5 有效期过滤**

- 法律场景：输入一个年份，只显示当时有效的节点（`start_year ≤ t < end_year`）。

#### F5. Inbox 与 Digest

**F5.1 学习时：只收集**

`knowrary article <文章>`（或 Claude Code skill `knowrary-import`）落 md、写 learned 日期、做初步关联、缺的概念建 stub。不选目录、不想位置。新节点处于 inbox 状态。

**F5.2 草稿放置（程序做）**

导入或定时任务之后，对每个 inbox 节点：

1. 确定目标分组：优先取结构族边指向的父节点所在分组；否则取 `field`；否则由 Curator（LLM）判断。
2. 在目标分组内找锚点：与新节点关系权重最高的已定稿节点。
3. 从锚点向外螺旋搜索空位（网格步长），**只在该分组框内部**，不与任何元素重叠。
4. 找到 → 写入 layout 为 draft；找不到 → 留在 inbox。
5. **绝不**扩大分组框、**绝不**移动已有元素。

**F5.3 集中画图时：Digest**

打开 Digest 视图，按分组列出：

- 本分组新增的草稿节点（可一键"全部定稿"，也可逐个拖）。
- 仍在 inbox 的节点（分组内没空位，或无法判断归属）。
- **跨分组新桥**：新节点连到其他分组的边（如 KV cache ⟷ 存储器层次结构）。这是学习面广时最有价值的一栏。
- 疑似重复：aliases 或 name 高相似的节点对，提示合并。
- 被引用最多的 stub，建议优先补写。

**F5.4 边不需要人工摆放**

边永远自动画。用户只在个别边上调拐点，这些边记进 layout。因此 Inbox 只关心节点。

#### F6. Agent 能力（复用 knowrary.py）

| 能力 | 现状 | 本项目改动 |
| --- | --- | --- |
| 关系抽取（learn） | 已有（`article` 命令 / skill） | 输出类型必须映射到族；写 learned 日期；触发草稿放置；走 `learn` 角色 |
| 图分析推荐（review） | 待重建（旧 kg.mjs 已弃用） | 含"跨分组桥"和"draft 未定稿超过 N 天"；走 `review` 角色 |
| 关系校验 | 无 | 对单条边给出成立/不成立、置信度、依据 |
| 分组判断（Curator） | 无 | inbox 节点无法用规则判断归属时调用 |
| 合并去重 | 无 | Digest 中列出，用户确认后合并 md 与关系 |
| 潜在方向草稿 | 无 | 后期 |

Agent 边界不变：**只提议，不自动写入 md**；layout 的 draft 是唯一允许程序直接写的地方，且用户随时可覆盖。

#### F7. 写回与同步

- md 写回按区块解析（frontmatter + `## 关系` 区块，`knowrary.py` 已有实现），只改关系区块和 frontmatter 指定字段，其余原文逐字保留。
- 写回前备份到 `.knowrary/backup/<timestamp>/`，vault 纳入 git。自动 commit 可配置，默认按一次确认批次提交，并在提交信息中记录变更摘要。
- 文件监听（watchfiles）：用户在 Obsidian 里改了 md，服务重新解析该文件并通过 WebSocket 推送前端刷新。
- 并发：服务对单个文件加写锁；前端在文件被外部修改后禁用该节点的关系编辑直到刷新完成。
- layout.json 写入采用整文件原子替换（写临时文件后 rename）。

#### F8. 复习提醒（遗忘曲线）

**F8.1 目的**

学过的东西不复习会忘。系统不评价学习顺序，只回答一个问题：**哪些节点到了该复习的时间点**。

**F8.2 数据**

- `learned`（frontmatter）：首次入库日期，导入流程已在写。
- `.knowrary/review-log.json`：复习历史，程序维护，不进 md：

```json
{
  "schema_version": 1,
  "nodes": {
    "tlb": { "reviews": ["2026-09-11", "2026-09-13"], "next_due": "2026-09-17" }
  }
}
```

  没有记录的节点视为 0 次复习，以 `learned` 为起点计算。
- 为什么不写进 md：复习记录是"我的行为"不是"知识"。每次点复习都改 md 会产生 git 噪音、与 Obsidian 编辑冲突、还要走 ChangeSet 确认。这个文件丢了只丢复习历史，知识不受影响。

**F8.3 算法**

- 首版固定间隔：第 n 次复习后的下次到期 = 本次日期 + `[1, 2, 4, 7, 15, 30][n]` 天；超过 6 次后每 60 天。
- 到期 = `today ≥ next_due`；逾期天数用于排序。
- 预留"记得 / 模糊 / 忘了"三档反馈：忘了 → 间隔序号回到 0；模糊 → 序号不变；记得 → 序号 +1。首版只做"已复习"一键（等价于记得）。

**F8.4 呈现**

- 结构视图：到期节点角标（黄 = 到期，红 = 逾期 > 7 天），关系族过滤旁加"只看待复习"。
- Digest 增加"待复习"栏：按逾期天数排序，显示 learned、上次复习、复习次数；点"已复习"追加记录并重算 `next_due`。
- 右侧详情面板显示该节点的复习历史。
- 命令行 `knowrary review-due` 输出到期列表，便于 cron / 每日提醒。

### 3.4 数据契约与版本规则

系统拆成三类数据：Markdown 是知识内容与关系的真相源；`index.json` 是可重建的解析缓存；`layout.json` 是结构视图的用户视图数据。任何一类数据都不能隐式覆盖另外两类。

#### 3.4.1 index.json 契约

```json
{
  "schema_version": 1,
  "revision": 17,
  "generated_at": "2026-09-10T10:00:00Z",
  "nodes": [],
  "edges": [],
  "families": [],
  "stubs": []
}
```

`index.json` 只包含渲染和检索所需的派生字段，不包含正文、坐标或用户视图状态。解析失败的文件必须进入 `errors` 列表并在界面提示，不能静默丢弃节点或边。

#### 3.4.2 layout.json 契约

`layout.json` 只保存结构视图的节点位置、分组、引用卡、便签、图片、折叠状态和手工边拐点。写入采用 revision 乐观并发控制：客户端提交时携带 `base_revision`，服务端版本不一致则拒绝覆盖并要求重新加载。

```json
{
  "schema_version": 2,
  "revision": 17,
  "updated_at": "2026-09-10T10:00:00Z",
  "groups": {}, "nodes": {}, "refs": [], "notes": [], "images": [], "edges": {}
}
```

服务启动时校验 layout 引用的节点、分组和资源。缺失引用移入诊断列表，不删除用户数据；Markdown 已删除的节点从画布投影中移除并回到可清理的孤立布局记录。

#### 3.4.3 ChangeSet 契约

所有 Markdown 写回都通过可审查的 ChangeSet：

```json
{
  "base_revision": 17,
  "changes": [{ "type": "add_edge", "source": "transformer", "target": "bert", "relation": "演化为", "year": 2018, "evidence": [], "confidence": 1 }]
}
```

ChangeSet 先展示预览，用户确认后才执行。执行前生成备份，执行后重新解析并推送新 revision；冲突时保留原文件，不强制覆盖。

### 3.6 X6 渲染细节与性能守则

**图实例配置：**

```javascript
const graph = new Graph({
  container, autoResize: true,
  async: true,        // 异步渲染
  virtual: true,      // 只渲染视口内元素（压测中 pan 从 25ms 降到 17ms）
  panning: true, mousewheel: { enabled: true, modifiers: null },
  embedding: { enabled: true, findParent: 'bbox' },   // 拖入分组框
  connecting: { router: 'orth', connector: 'rounded', allowBlank: false },
})
graph.use(new History()); graph.use(new Selection()); graph.use(new Keyboard())
```

**节点形状：纯 SVG，不用框架组件。**

```javascript
Graph.registerNode('kg-node', {
  inherit: 'rect', width: 160, height: 60,
  markup: [{ tagName: 'rect', selector: 'body' }, { tagName: 'text', selector: 'title' },
           { tagName: 'text', selector: 'desc' }],
  attrs: { body: { rx: 6, ry: 6, fill: '#fff', stroke: '#999' },
           title: { refX: 10, refY: 20, fontSize: 13, fontWeight: 600 },
           desc:  { refX: 10, refY: 40, fontSize: 11, fill: '#666', textWrap: { width: -20, ellipsis: true } } }
})
// draft 状态：stroke-dasharray '4 3'，fill 更浅
```

理由：第一版写的"自定义 Vue/React 组件节点"在几千节点下会成为瓶颈（每个节点一个组件实例 + foreignObject）。框架组件只用于面板类 UI。

**边样式：按族注册 5 种。**

```javascript
const FAMILY_STYLE = {
  依赖:   { stroke: '#8a8a8a', strokeWidth: 1,   targetMarker: 'block' },
  演化:   { stroke: '#e07b1a', strokeWidth: 2.5, targetMarker: 'block' },
  对照:   { stroke: '#8e5bd6', strokeWidth: 1,   strokeDasharray: '5 4', targetMarker: null },
  弱关联: { stroke: '#bbb',    strokeWidth: 1,   strokeDasharray: '2 3', targetMarker: null },
  结构:   null,  // 默认不画线，表现为嵌套
}
```

**嵌套与折叠：** 分组用 X6 的 parent/children；折叠时移除子元素并把分组节点换成"簇卡片"形状；展开时反向。折叠状态存 layout。

**投影模型：** X6 的数据模型里**只放当前可见的元素**（展开分组的直接子元素 + 折叠分组的簇卡片 + 两端可见的边）。折叠掉的子树不进模型。这样无论 vault 多大，X6 模型规模始终受可见元素预算约束。

**性能守则：**

1. 视口可见元素常规目标为 300～600，超过 1500 时必须由 LOD 自动折叠。
2. 节点 markup ≤ 3 个 SVG 元素；不用 foreignObject。
3. 拖拽过程中不写盘，松手后节流写 layout。
4. 边 label 只在 zoom > 0.8 时渲染。
5. 全图搜索、度数统计等在服务端或 Web Worker 做，不遍历 X6 模型。

### 3.7 LOD 算法

```
输入：zoom、layout.groups、常规预算 B=600，降级上限 B_max=1500
1. 按缩放阈值给每个分组初始状态：depth 0 展开；depth 1 在 zoom≥0.35 展开；depth≥2 在 zoom≥0.7 展开
2. 应用 pinned 覆盖
3. 统计视口内可见元素数 n
4. while n > B：选择视口内、深度最大、未 pinned 的已展开分组，折叠之，重新统计；若仍超过 B_max，继续折叠并显示性能提示
5. 输出可见子集，diff 上一帧，增量 add/remove 到 X6
```

折叠簇卡片显示：分组名、节点数、度数 top-5 的节点名。跨分组边在两端任一侧折叠时聚合为 `簇A → 簇B (n)`。

### 3.8 历史视图布局

```
输入：所选时间线（一个或多个 layout 分组，默认"全部"）内有 year 的节点、两端有 year 的边
1. X = scaleLinear(yearMin..yearMax → 0..W)；紧凑模式下把间隔 > 20 年的区段压缩到固定宽度
2. Y：所选分组的每个直接子分组一条泳道（选"全部"时按顶层 field）；泳道内按 year 排序，扫描线放置，重叠则下移一行
3. 边：演化族全画；依赖/对照族按开关；跨所选分组的边照常画
4. 时间滑块 t：过滤 year ≤ t；新出现的节点用 300ms 渐显动画
5. 多选叠加：各选中分组的泳道按分组分块并排，块之间留空行
```

历史视图坐标不持久化，每次进入重算。

### 3.9 草稿放置算法

```
输入：inbox 节点 n，index，layout
1. 目标分组 G：
   a. n 的结构族边指向的父节点所在分组
   b. 否则 field 对应的顶层分组
   c. 否则调用 Curator → 返回分组 id 或 "unknown"（留 inbox）
2. 锚点 a：G 内与 n 关系权重最高的 final 节点（权重：演化 3、依赖 2、结构 2、对照 1、弱关联 0.5）
3. 从 a 的右侧开始螺旋搜索（步长 40px），候选矩形 160×60
4. 候选必须完全在 G 的框内，且与 G 内所有 nodes/refs/notes/images 不重叠（留 16px 间距）
5. 找到 → nodes[n] = { …, state: "draft", anchor: a, placedAt: today }
   找不到 → 留 inbox，Digest 中提示"分组已满"
```

禁止事项：不扩大分组框、不移动任何已有元素、不跨分组放置。

- 配置文件 `.knowrary/llm.local.json`，模板 `.knowrary/llm.example.json` 入库；`.gitignore` 忽略 `*.local.json`。环境变量 `KNOWRARY_LLM_CONFIG` 可指向别处。没有配置文件时退回 `claude -p`。
- `providers`：任意多个命名后端，三种类型：`claude-cli`（复用 Claude Code 登录，无密钥）、`anthropic`（官方 API）、`openai`（OpenAI 兼容协议：OpenAI、DeepSeek、通义、Ollama、vLLM 等）。`api_key` 支持 `env:VAR` 引用环境变量。零第三方依赖，全部走 urllib。
- `roles`：按用途指向 provider。首版两个角色：`learn`（文章拆节点、关系抽取）和 `review`（校验、Curator、去重）。**两个角色故意允许指向不同模型**：单一模型有自己的偏差，用第二个模型审第一个模型的产出，是最便宜的纠偏手段。
- 命令行 `--llm <provider>` 临时覆盖角色默认，`--model` 临时覆盖模型；`knowrary llm list / test` 查看配置与连通性。
- 服务端 `/api/llm` 读写同一文件；前端设置页（多 LLM、角色指派）是后期工作，首版先把 `learn` 链路做扎实。
- 开源保护：`knowrary check` 发现任何 `*.local.json` 被 git 跟踪时报错。

新增 validate prompt 沿用第一版 F6.2。

Agent 的边界：只写 layout 的 draft 条目；任何 md 变更都进确认队列。

## 第四部分：关键决策与注意点

### 4.1 核心决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 渲染引擎 | X6 单引擎 | 压测证明可用；编辑能力最完整；双引擎的同步成本不值 |
| 全局纵览方式 | LOD 折叠簇，不是万点全画 | 几千元素同屏时缩放 6~13fps；折叠簇也更符合"大框套小框"的阅读习惯 |
| 坐标存放 | 独立 layout.json | 视图与内容分离；支持引用卡；换引擎不动数据 |
| 图的数量 | 一张全局图 + 分组 | 用户要"全局纵览也能看细节"；跨领域桥自然可见 |
| year | 可选，作为进入历史 tab 的开关 | 结构性知识没有年份；强制填写会污染数据 |
| 关系类型 | 5 个族固定，具体类型可增长 | 渲染稳定；LLM 造新类型不再导致丢边 |
| 边方向 | 单向写入 + 解析推导反链 | 双向回填导致两处漂移 |
| 自动摆放 | 只放草稿、只在分组内、不动已有元素 | 保住手工布局质量，同时不打断学习 |
| 节点实现 | 纯 SVG | 框架组件节点在几千节点下是性能陷阱 |
| 备份 | git + 写前快照 | 与 Obsidian 并发编辑时可回滚 |

### 4.2 常见坑与对策

| 坑 | 表现 | 对策 |
| --- | --- | --- |
| 全图毛线球 | 缩到最小时几千节点糊成一团 | 可见元素预算 + 自动折叠 |
| 框架组件节点 | 2000 节点后掉帧、内存暴涨 | 纯 SVG 节点，框架只做面板 |
| 程序乱摆位置 | 用户画好的结构被打乱 | 三态；程序只写 draft、只在分组内、不动 final |
| 新类型丢边 | LLM 造的类型不在清单里，边消失 | 未登记类型落"弱关联"族并提示，不隐藏 |
| 反链漂移 | 双向回填后两侧不一致 | 单向写入，反链推导 |
| 同一节点多处需要 | 复制节点导致重复 | 引用卡 |
| 与 Obsidian 并发编辑 | 写回覆盖用户刚改的内容 | 文件监听 + 写锁 + 写前备份 + git |
| 分组框被撑爆 | 自动放置扩大分组，挤压相邻分组 | 禁止扩大分组；放不下留 inbox |
| year 缺失导致历史图残缺 | 演化边缺少有效年份 | 不自动伪造年份；review 提示补充节点或边的 year |
| 外部图稿兼容成本 | 外部图形、折线和特殊样式难以统一 | 首版不迁移，后续作为独立工具设计 |

### 4.3 首版范围与后续扩展

首版不处理 ProcessOn、draw.io 等外部图稿迁移。用户手动创建 Markdown 和初始分组，先验证“知识文件 → Inbox → 画布 → 保存恢复”的闭环。未来迁移作为独立工具设计，输入格式、特殊图形映射和坐标导入不进入核心服务。

首版完成后，再按独立能力扩展：外部图稿迁移、增量布局优化、关系校验、去重合并、更多历史事件类型、G6 WebGL 投影层，以及多人协作。

### 4.4 边界：这个系统不做什么

- 不做 md 编辑器：写内容在 Obsidian。
- 不做通用绘图：形状只有节点、分组、便签、图片，不支持任意图形。
- 不做全自动整图布局：自动布局只存在于历史视图（X 被时间锁死）和草稿放置（只在分组内找空位）。
- 不做多人协作：单用户本地。

## 第六部分：落地路线图

### 阶段 0：数据层整理（1~2 天）

1. knowage vault `git init`，首次提交。
2. `relation-types.json` 加 family / inverse / canonical 字段。
3. 解析器：读取 `::` 关系语法，兼容旧箭头语法；完成方向归一、未知类型落默认族、stub 识别。

5. ✅ LLM 配置文件与 learn / review 双角色（2026-09-10 完成，`knowrary article` 已走配置）。

### 阶段 1：最小闭环（2 周）—— 直接解决当前痛点

1. 本地服务（Python / FastAPI）：解析 vault → index.json；读写 layout.json；文件监听。
2. 手动创建 10～30 个示例 Markdown 和初始 layout 分组。
3. X6 结构视图：纯 SVG 节点、5 族边样式、分组嵌套、手动折叠/展开、拖拽持久化、右侧 md 面板、双击打开 Obsidian。
4. Inbox 托盘：列出不在 layout 中的节点，拖入画布即 final。
5. **验收标准**：手动创建的节点能被解析；新节点进入 Inbox；拖入后刷新位置不变；修改布局不会改变 Markdown；关系变更经确认、备份后才能写回。

### 阶段 2：视图完善（1~2 周）

1. LOD 自动折叠 + 可见元素预算 + 钉住。
2. 引用卡、便签、图片、连线拐点。
3. 撤销/重做；右键改边类型并写回 md（含确认、备份、git commit）。
4. 搜索、关系族过滤、悬停高亮。
5. 复习提醒（F8）：review-log.json、到期计算、角标、Digest 待复习栏、`review-due` 命令。

### 阶段 3：历史视图（1 周）

1. 历史 tab：X=year 自动布局、泳道、紧凑模式。
2. 时间滑块与生长动画；被激活金色虚线。
3. 时间线选择器（按 layout 分组切换 / 多选叠加）；有效期过滤。

### 阶段 4：Inbox 自动化（1~2 周）

1. 草稿放置算法。
2. Digest 视图：草稿、跨分组桥、重复、stub。
3. Curator 分组判断；重建 review（桥、草稿超期），走 review 角色。

### 阶段 5：持续

1. 关系校验、合并去重、潜在方向草稿。
2. 规模化验证：造 6000 节点假数据跑真实 UI。
3. 若超过万级且 LOD 不够，评估 G6 WebGL 渲染层替换。

## 附录 A：X6 性能压测

**方法**：本机 Chrome（headless，puppeteer-core 驱动），X6 2.x，`async: true`，每节点 1.5 条边（1 条实线 + 0.5 条虚线），节点为 rect + 文字。1:1 场景视口 1600×1000，可见约 150~800 个元素；全图场景 `zoomToFit` 后测量。帧时间取 rAF 间隔平均值，16ms 即 60fps。

**A.1 局部视图（1:1）**

| 节点 | 边 | virtual | 加载 | 拖动平均 | 拖动峰值 | 缩放 | 拖节点 | 内存 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 500 | 748 | 否 | 193ms | 50ms | 886ms | 24ms | 17ms | 10MB |
| 1500 | 2248 | 否 | 294ms | 21ms | 46ms | 44ms | 17ms | 21MB |
| 3000 | 4498 | 否 | 878ms | 25ms | 46ms | 67ms | 19ms | 39MB |
| 6000 | 8998 | 否 | 920ms | 28ms | 59ms | 125ms | 48ms | 79MB |
| 10000 | 14998 | 否 | 2373ms | 25ms | 50ms | 160ms | 60ms | 106MB |
| 500 | 748 | **是** | 76ms | 16ms | 26ms | 18ms | 17ms | — |
| 1500 | 2248 | **是** | 221ms | 16ms | 34ms | 18ms | 17ms | 22MB |
| 3000 | 4498 | **是** | 444ms | 17ms | 35ms | 20ms | 17ms | 27MB |
| 6000 | 8998 | **是** | 959ms | 17ms | 42ms | 21ms | 16ms | 59MB |
| 10000 | 14998 | **是** | 1485ms | 28ms | 188ms | 74ms | 27ms | 174MB |

**A.2 全图视图（zoomToFit，virtual 开）**

| 节点 | 视口内元素 | 拖动平均 | 拖动峰值 | 缩放平均 | 缩放峰值 |
| --- | --- | --- | --- | --- | --- |
| 1500 | 1150 | 23ms | 44ms | 33ms | 40ms |
| 3000 | 909 | 27ms | 46ms | 74ms | 131ms |
| 6000 | 1055 | 34ms | 69ms | 143ms | 222ms |
| 10000 | 452 | 37ms | 112ms | 161ms | 269ms |

**结论**：

1. `virtual: true` 必开。
2. 6000 节点以内，只要视口内可见元素在几百个，拖动、缩放、拖节点全部满帧。
3. 10000 节点可用但有抖动（拖动峰值 188ms，缩放 74ms）。
4. 几千个元素同屏时缩放掉到 6~13fps。**全局纵览必须靠 LOD 折叠把可见元素压到几十到几百个**，这是 2.3 中"可见元素预算 1500"的来源。
5. 压测节点是最简 SVG。真实节点 markup 更复杂、加上分组框和边标签，实际余量比表中略小，因此性能守则要求节点 markup ≤ 3 个元素、边标签 zoom > 0.8 才渲染。
